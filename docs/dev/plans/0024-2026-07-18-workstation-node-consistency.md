## Objective

Plan and execute workstation-wide Node consistency through an agent-loop-driven migration. The top-level agent remains the orchestrator and overseer while fresh workers make bounded updates and fresh reviewers independently verify each completed slice. The outcome is the minimum practical variation in Node runtimes and user-scoped packages, no accidental divergent Node selection unless a software-specific requirement demands it, continued correct operation of all in-scope software, and a reproducible path for future Node upgrades across shells, services, packages, and connected Codex/OpenClaw surfaces.

Private operator procedure, excluded from docs publishing: `docs/internal/workstation-node-upgrade.md`.

## Scope

- Linux and WSL shell startup, PATH precedence, Node selection, npm, Corepack, pnpm, user-scoped JavaScript packages, executable shims, and native-addon rebuild risk.
- User systemd units, drop-ins, timers, generated owner templates, and other maintained sources that emit Node, OpenClaw, Codex, or package-manager paths.
- OpenClaw gateway and adjacent live services that execute Node or Node-installed tools.
- Codex commands and MCP launch configuration whose runtime path can diverge from the workstation policy.
- Windows Node selection only where it is inherited into WSL or is needed to align the workstation's default major and patch policy.
- An inventory/checker and receipts ledger that make migration, validation, rollback, and future upgrades reproducible.

## Non-goals

- Forcing every repository to use the same package-manager version when its checked-in `packageManager` contract selects another version.
- Replacing Bun, Deno, Electron-bundled Node, application-embedded runtimes, container images, remote runners, or platform-specific runtimes that have a documented owner and requirement.
- Upgrading application versions merely because their current installation is being moved to the canonical runtime.
- Removing operating-system Node, NVM, old package trees, or rollback copies before zero-reference and live-validation proof.
- Hiding legitimate per-project requirements behind compatibility shims or silently changing repo engine contracts.

## Target Policy

1. Homebrew `node@24` is the canonical Linux/WSL Node owner for this migration. Its `opt` path supplies the active LTS line and currently resolves to Node 24.18.0.
2. A single user-owned stable switchpoint under `~/.local/share/node/current` points to the selected Homebrew `opt` runtime. Stable executables under `~/.local/bin` expose Node tooling to shells and services. Versioned Cellar paths and NVM version directories are never written into maintained runtime configuration.
3. Shell startup places the stable user bin ahead of inherited Linux and Windows Node paths and does not auto-activate NVM. NVM may remain available as an explicit exception tool until retirement, but it does not own the default shell.
4. Corepack owns pnpm selection. Outside a repository it provides the documented workstation default; inside a repository it honors that repository's checked-in `packageManager` declaration. npm, pnpm, Bun, or another manager remains valid when a project explicitly declares it.
5. User-scoped CLIs are installed once through PNPM_HOME or their maintained standalone installer. Local workspace CLIs use intentional stable links. Packages are reinstalled under the canonical runtime; NVM package trees are not copied.
6. Operating-system Node and per-project runtimes are exceptions only when an engine, platform, packaging, or owner contract proves they are required. Every exception records owner, consumer, required version range, invocation path, validation, and removal/review condition.
7. Node major changes require an engine-contract audit before cutover. A project such as CodeGraph that currently requires Node below 25 blocks a workstation-wide move beyond Node 24 until its owner contract changes or it receives an explicit isolated runtime.

## Agent Loop And Change Control

- The top-level agent owns the plan, phase ordering, shared inventory, risk decisions, stop conditions, receipts, and final completion audit. It does not take over implementation slices that can be assigned cleanly.
- Each mutation slice goes to a fresh bounded worker with explicit owned files or live surfaces, required preconditions, validation commands, rollback, and a stop-after-report boundary.
- A fresh reviewer independently inspects the worker's complete changed surface, source owner, generated consumers, current runtime readback, tests or checks, rollback safety, and receipts. Reviewers do not rely only on worker summaries.
- Accepted reviewer findings return to a fresh repair worker, followed by another fresh review. A lane closes only when no accepted or actionable findings remain.
- Agents never switch the shared checkout branch while sibling work is active. Service restarts and path cutovers are serialized even when read-only inventory or source-owner work runs in parallel.
- Before Codex-related verdicts or mutations, the acting worker personally inspects the relevant sibling `../codex` source and cites the exact files and lines that establish the launch or MCP contract.
- Any unexplained service regression, missing owner source, secret-bearing configuration risk, moving target, or inability to prove rollback stops that slice and returns control to the orchestrator.

## Phase 1: Inventory And Checker

1. Build a machine-readable inventory of every Node executable and manager, resolved version, ABI/N-API version, PATH position, package prefix, Corepack/pnpm behavior, global package and engine contract, native addon, executable shim, service reference, timer, owner template, Codex command, MCP launch command, and inherited Windows path.
2. Classify each runtime reference as canonical, explicit exception, stale, generated, backup/quarantine, or unresolved. Record the owning file or package and live consumer.
3. Add a read-only checker that fails on versioned NVM/Cellar paths in maintained configuration, default-shell divergence, direct pnpm bypass of repo Corepack pins, dangling package links, unresolved native-addon rebuilds, unowned exceptions, and canonical-path/version mismatch.
4. Make checker output deterministic and secret-safe. It may report paths, package names, versions, unit names, and health states, but never environment secret values.
5. Capture a pre-migration receipts baseline and exact rollback inventory before the first runtime mutation.

Exit gate: the inventory accounts for every discovered default/runtime path and package owner; every unresolved item has an owner and next action; the checker reproduces the known divergence without changing state.

## Phase 2: Shell And User Packages

1. Create the stable user Node switchpoint targeting Homebrew `node@24`; expose the canonical Node, npm, npx, and Corepack commands through the stable user bin without versioned paths.
2. Simplify zsh and bash startup so the stable user bin wins deterministically, inherited Windows Node paths cannot take precedence, and NVM is explicit rather than auto-activated. Verify login, interactive, and non-interactive shells.
3. Remove the direct global pnpm executable that bypasses Corepack, enable Corepack at the stable runtime, set and document the outside-repo default, and prove representative repositories receive their declared pnpm, npm, or Bun version.
4. Reinstall the exact existing versions of retained global CLIs into PNPM_HOME or their supported standalone location. Preserve standalone Codex, use one OpenClaw installation, recreate only intentional local workspace links, and remove duplicates only after command-level comparison and smoke proof.
5. Reinstall packages with native addons under the canonical runtime. Do not copy NVM `node_modules`; prove addon loading and dependent CLI behavior on Linux.

Exit gate: all fresh shell modes select the stable Node 24 runtime without warnings; package-manager selection matches global and per-project policy; each retained CLI has one authoritative installation and passes a version/help or owner-specific smoke test; old trees remain available for rollback.

## Phase 3: Owner Templates, Systemd, And Codex MCP

1. Locate and update the maintained owner templates or installers that generate service units before editing generated user units. Where no owner exists, record and assign one rather than normalizing only the generated copy.
2. Replace versioned Node executable and PATH entries with the stable Node path. Replace NVM-installed Codex and OpenClaw paths with their stable user-scoped commands. Preserve arguments, environment ownership, credentials handling, restart policy, and timer relationships.
3. Regenerate or reconcile user units from their owners, then run `systemd-analyze --user verify` or the narrow equivalent before daemon reload.
4. Inspect sibling `../codex` for the exact command and MCP process-launch behavior, then update Codex settings and user-scoped MCP commands to inherit or explicitly use the stable runtime as their contract requires.
5. Run the inventory/checker again and require maintained owner sources, generated units, installed unit readback, and Codex MCP readback to agree.

Exit gate: no maintained owner or active unit contains a versioned NVM/Cellar Node path; Codex and MCP commands resolve through supported stable paths; installed systemd readback matches source; inactive and timer-driven units have static proof before live activation.

## Phase 4: Live Validation With Gateway Last

1. Validate and restart services individually, from lowest blast radius to highest. For each service capture pre-state, restart result, MainPID executable, command line, journal window, bound endpoint or output artifact, and owner-specific success condition.
2. Exercise timer and one-shot services through a bounded dry run or supported live invocation. A healthy process alone is insufficient; prove its actual expected yield without causing duplicate external actions.
3. Validate shell CLIs and package consumers after service changes so a working daemon cannot mask an interactive-path regression.
4. Migrate and restart the OpenClaw gateway last. Prove installed unit readback, canonical Node executable, gateway health, representative agent/tool behavior, channel delivery where safe, and Codex MCP availability.
5. Run a fresh reviewer over the complete changed runtime surface and rerun the checker after all services settle.

Exit gate: every enabled, active, timer-driven, or operationally required service has current owner-specific live proof; the gateway runs last on the canonical runtime; no relevant new engine, ABI, startup, or module-resolution errors appear in the bounded journals.

## Phase 5: Cleanup And Quarantine

1. Re-run a whole-workstation reference scan across shell startup, maintained configs, owner templates, installed units, timers, process command lines, executable links, Codex settings, MCP configuration, and package metadata.
2. Require zero live and maintained references before removing any NVM runtime, operating-system Node, generic Homebrew Node, alternate Homebrew major, duplicate global package tree, or stale executable.
3. Quarantine ambiguous artifacts and old unit backups with a manifest, reason, original location, retention date, and recovery command. Do not leave backup files in systemd discovery paths.
4. Remove the two known dangling `@openclaw/fs-safe` links only with their retired NVM package trees or after proving no consumer.
5. Align Windows NVM to the canonical Node 24 patch policy, while keeping Windows execution an explicit platform surface rather than a WSL PATH fallback.
6. Produce the future upgrade runbook and checker command: inventory, engine/exception audit, Homebrew update, stable-target verification, native package rebuild decision, representative CLI checks, serialized service restart and live proof, gateway-last validation, soak, cleanup, and rollback.

Exit gate: the only default Linux/WSL Node is the stable Homebrew `node@24` target; every remaining alternate runtime is a documented and tested exception; retired managers and package trees have zero-reference proof and a recorded cleanup receipt.

## Rollback

- Before each phase, store timestamped copies or exports of changed shell files, user units and drop-ins, package inventories, manager state, stable-link target, enabled/active service state, and application health readbacks outside systemd discovery paths.
- Keep NVM 24.14.0, operating-system Node 25.9.0, the existing OpenClaw package tree, and other required prior runtimes installed until all acceptance gates and the soak period pass.
- Runtime rollback is atomic: repoint the stable `current` link to the recorded prior target, restore only the affected shell or owner/unit files, daemon-reload, and restart affected services one at a time.
- Package-manager rollback restores direct pnpm 9.15.5 only if Corepack cutover fails, then verifies both outside-repo and repo-pinned behavior.
- Package rollback reinstalls recorded exact versions from their source; never copy native-addon trees across runtimes.
- A failed service migration rolls back only that service and its owner-generated configuration while already validated services remain canonical.
- A gateway failure restores its prior unit and Node/package path immediately, then proves gateway and channel health before any further migration.
